# 通用文本审稿设计

## 背景与目标

审稿功能为内容创作提供第一轮判断和连续沟通能力。小编提交文本后，审稿 agent 根据已确认的通用标准提出意见；小编提交修改稿或逐条回应；agent 持续复审，直到小编明确确认通过。沟通过程可以产生新的通用审稿偏好，但任何新标准都必须经过人工确认后才影响后续审稿。

第一阶段面向所有文本，不绑定公众号、小红书或其他平台。审稿上下文只绑定当前会话，不支持跨会话继续同一篇内容。

## 设计决策

采用“插件负责能力与状态，Skill 负责审稿方法”的混合方案。Skill 提供可替换的审稿流程、默认维度、意见格式和标准提炼方式；插件提供审稿服务、模型调用操作、会话状态、标准版本和结构化结果。

纯 Skill 无法可靠保存全局标准、执行人工确认和维护结构化审稿状态。纯插件会把容易变化的判断方法固化到代码或配置中。混合方案将可变的判断方法与必须持久化的产品状态分开，同时保留自然语言会话入口和未来工作流编排能力。

## 用户流程

1. 小编在当前会话中用自然语言请求审稿，例如“审稿这篇内容”。
2. Skill 识别审稿意图，加载当前生效的全局标准，并调用插件创建审稿上下文。
3. agent 执行首轮审稿，报告使用的标准版本、必须修改项、建议优化项、判断依据和修改建议，并给出“仍需修改”或“建议通过”。
4. 小编在同一会话中提交修改稿或回应具体意见。
5. agent 创建新的审稿轮次，报告新问题、已解决问题、仍未解决问题和由修改引起的新问题。
6. agent 可以提出候选标准变更，说明候选内容、来源、适用范围和影响；候选变更不会自动生效。
7. 小编明确确认或拒绝候选变更。确认后插件发布新的全局标准版本，拒绝后候选变更仅保留在当前会话记录中。
8. agent 给出“建议通过”后，小编仍需明确确认通过；确认后审稿状态变为“已确认通过”。

## 组件职责

### 审稿 Skill

审稿 Skill 负责生成和解释默认审稿标准，按标准执行首轮审稿和复审，组织稳定的审稿输出，并从小编反馈中提炼候选标准变更。Skill 不直接持有审稿状态，不直接写入全局标准，也不能绕过人工确认发布标准。

默认 Skill 先生成一版通用标准，由小编确认后作为起点。标准覆盖目标与受众、结构、论证、表达和事实风险等通用维度；具体维度和规则属于 Skill 的可替换内容。

### 审稿插件

审稿插件注册审稿服务和模型可调用操作，维护当前会话的审稿上下文，持久化已确认的全局标准及其版本，提交候选标准变更，并记录可恢复的会话事件。插件负责校验操作前提，例如没有活动审稿时拒绝复审和确认通过，没有候选标准时拒绝确认标准变更。

第一版不增加独立审稿面板。会话 UI 复用现有消息和工具结果展示；将来可以增加审稿状态、候选标准确认和意见勾选 UI，但不改变审稿服务接口。

### 工作流消费方

未来的热点、写作、排版或发布工具通过插件提供的结构化能力组合审稿流程，不通过解析会话中的 Markdown 报告判断结果。第一版只预留接口，不自动执行完整的修改循环。

## 数据模型

全局审稿标准是带版本的结构化文档。每条标准包含稳定标识、审稿维度、判断规则、问题优先级、可选正反例、启停状态、来源、版本和更新时间。来源区分默认生成、人工新增和沟通提炼。

审稿上下文包含审稿上下文标识、当前会话标识、开始时固定的标准版本、原始文本、当前文本或最近一次小编回应、审稿轮次、每轮结果、未解决意见、候选标准变更和当前状态。

审稿状态至少包括“审稿中”“等待修改”“等待确认标准”“建议通过”“已确认通过”。“建议通过”是 agent 的建议，不是终态；只有小编明确确认后才进入“已确认通过”。

一次审稿在开始时固定使用当时生效的标准版本。之后全局标准版本发生变化，不会改变当前审稿历史或已产生的判断。小编可以明确要求按新版本重新审稿，重新审稿应产生新的轮次并记录所使用的标准版本。

## 服务与操作

插件提供审稿服务，供 Skill 和未来工作流使用以下结构化操作：

- `startReview(text, options?)` 创建当前会话的审稿上下文并启动首轮审稿。
- `reviewRevision(textOrResponse)` 在当前审稿中提交修改稿或小编回应并启动复审。
- `confirmStandardChange(candidateId, decision)` 确认或拒绝候选标准变更。
- `confirmReviewPassed()` 记录小编对“建议通过”的明确确认。
- `getReviewState()` 返回当前会话的审稿状态、轮次、标准版本和未解决事项。

这些操作的模型可见参数和结果由消费方定义，服务接口不包含 UI、传输或具体工作流实现细节。模型调用操作必须在执行处校验状态，不能只依赖 Skill 指令或工具 schema 限制。

未来工作流可读取类似下列结构化结果：

```ts
{
  status: "needs_revision" | "recommended_pass" | "passed",
  reviewId: string,
  revision: number,
  blockingIssues: number,
  suggestions: number,
  candidateStandardChanges: number
}
```

## 持久化与会话记录

影响模型判断的文本、审稿标准版本、审稿结论、意见状态、候选标准变更和人工确认结果都必须进入会话日志，保证恢复和回放时可以重建模型可见上下文。全局标准的正式版本独立持久化，并通过标准版本事件或等价的持久记录关联到审稿上下文。

标准更新只在完整确认和持久化成功后发布变更通知。写入失败不得产生新的生效版本，也不得让当前审稿上下文引用未提交的标准。

审稿插件和 Skill 都是可选组合项，不加入所有默认配置。启用插件后，它使用当前会话的日志和全局标准存储；插件卸载必须撤销服务、工具和事件注册，不留下失效贡献。

## 错误处理

没有当前文本时，`startReview` 拒绝创建空审稿并返回明确错误。没有活动审稿时，`reviewRevision`、`confirmReviewPassed` 和读取依赖活动审稿的操作返回状态错误。没有指定候选标准时，`confirmStandardChange` 拒绝执行。

当前审稿已确认通过后，继续提交修改稿必须显式创建新的审稿上下文或重新打开流程，不能隐式覆盖已确认的结论。过期或不存在的候选标准标识必须拒绝确认，避免把确认动作应用到错误规则。

标准候选的提炼失败只影响当前轮次的候选结果，不影响审稿结论。审稿模型调用失败必须保留已提交文本和上一轮持久状态，不能发布未完成的审稿结论。

## 工作流示例

```text
素材整理 -> 内容创作 -> 通用审稿
                         -> 仍需修改 -> 内容创作
                         -> 建议通过 -> 小编确认
                         -> 已确认通过 -> 排版或发布
```

内容创作节点负责修改文本，审稿节点负责返回结构化结论。标准候选的人工确认是独立动作，不应由工作流自动跳过；内容修改循环第一版仍由小编和 agent 在同一会话中完成。

## 第一阶段范围

第一阶段交付通用文本审稿 Skill、当前会话级审稿状态、首轮审稿、连续复审、分级意见、人工确认通过、全局标准候选变更与版本化保存，以及未来工作流可消费的结构化结果。

第一阶段不交付跨会话内容项目、平台专项规则、自动修改正文、自动确认通过、自动生效新标准、复杂审稿面板或后台异步审稿任务。

## 验证要求

验证必须覆盖首轮审稿加载正确标准版本、修改稿产生新轮次、意见解决状态稳定、会话恢复后状态一致、候选标准未经确认不影响全局标准、确认后新版本可被下一次审稿使用、当前审稿不因全局更新而改变依据、无效操作被插件拒绝、结构化结果可被工作流消费，以及插件卸载后注册贡献被移除。

产品可见行为应通过真实组合的 Harness 配置验证，而不是只通过手工构造的 Context 测试。模型可见文本、持久事件和工作流结果需要覆盖对应的快照或集成测试；服务状态转换和标准版本操作需要覆盖聚焦单元测试。
